02 / Native code

Ghidra makes compiled code
something we can inspect.

Ghidra / open-source analysis suite

“What does this function do, and who calls it?”

Developed by the NSA. Supports interactive analysis, automation and many processor architectures.

Disassembly

Read the machine instructions as assembly.

Decompilation

Reconstruct the logic as C-like pseudocode.

References & types

Follow callers, strings and data; improve names and structure as evidence accumulates.

Processor support and correct loading matter. Ghidra support for an arbitrary architecture is not implied by REA supporting Ghidra.

A closer look / Ghidra

The logic can survive.
The original names may not.

An illustrative source function
int add_values(int left, int right) {
    return left + right;
}
Illustrative recovered pseudocode
int FUN_00101000(int param_1,
                 int param_2) {
    return param_1 + param_2;
}

We can infer addition. Its purpose takes context: callers, data, inputs and observed behavior.

An authored teaching example, not an actual Ghidra output. Optimization can change code structure. Pseudocode is a reconstruction.

Native analysis / alternative engines

Different engines.
A related set of questions.

01

Hopper

A commercial disassembler and decompiler for exploring native programs.

REA can query its analysis database for procedures, instructions and references.

02

IDA / Hex-Rays

Native-code analysis with decompilation available through the relevant Hex-Rays components.

REA uses a configured IDA integration. Capabilities depend on the installation and license.

03

Kuna

An alternative decompiler provider for procedures, assembly and pseudocode.

Its REA adapter uses exported analysis. Some graph, memory and annotation operations remain unavailable.

These are provider choices. One installation does not need all four decompilers, and the providers do not expose identical capabilities.

Native analysis / supporting tools

Sometimes the useful answer
is a very small one.

GNU objdump

Inspect instructions, sections, symbols and relocations from the command line.

Useful for a quick, focused view of what is in an executable.

Rizin

A scriptable framework for binary inspection, disassembly and debugging.

Select the architecture and memory layout explicitly for raw firmware.

Cutter

A graphical interface built around Rizin.

REA offers a local bridge to a configured Cutter session.

pwntools

A Python toolkit used here for ELF layout and recorded crash inspection.

REA's documented offline workflows have specific Linux host requirements.

03 / Running programs

Now we can ask:
“What happened this time?”

GDB

Pause, step and inspect registers, memory and call stacks.

REA's persistent GDB sessions are Linux-only.

LLDB

A debugger used by REA's macOS native-call observation workflow.

Selected entry points can reveal calls and argument-register values.

Frida

Instrument a running app with scripts to observe calls, inputs and results.

Scripts run inside the target and can change its behavior.

pwndbg

Debugger assistance for understanding memory and program state.

Optional GDB/pwndbg context can supplement REA's recorded Linux crash workflow.

The important distinction

Possible behavior.
Observed behavior.

Static analysis

Read the artifact.

Find instructions, constants, relationships and candidate code paths.

“This function appears to encode a MIDI message.”

Runtime observation

Watch a particular run.

Record the calls, values or messages produced by a chosen action.

“Moving this control sent these bytes during the capture.”

A static reference is not proof of execution. A recorded run only covers the actions and interval that were observed.

04 / Firmware

Before reading the code,
find what the image contains.

Find the pieces

Binwalk

Identify embedded formats and candidate regions inside a firmware image.

A signature is a starting point for checking a region's actual structure.

Unpack the pieces

Unblob

Extract supported containers, compressed data and filesystem contents.

Keep the extracted files connected to their original artifact and offsets.

Package → regions → extracted components → native analysis

REA's integration uses caller-supplied tools on Linux. A custom format can require a dedicated decoder.

Electrical transitions
become protocol annotations.

sigrok-cli

Decoded values, annotation ranges and diagnostics tied to the supplied recording.

05 / Applications

An Android app has
more than one layer.

JADX

Turn DEX bytecode into Java-like code and inspect classes and methods.

Useful for tracing application logic; native libraries need a native analysis path.

Apktool

Decode resources, manifest data, strings and locale information.

Useful for understanding what the package declares and presents.

ADB

Work with a connected Android device or emulator.

Package inventories, processes, logs, screen captures and selected transfers.

JEB

A commercial analysis platform with an optional REA MCP connection.

Query project units and type or method pseudocode from the configured JEB client.

Applications / browser & web runtimes

Follow the application
across its boundaries.

Browser + CDP

Inspect page structure, scripts, network events and selected runtime behavior.

CDP is the browser's debugging interface. It also supports relevant Electron inspection paths.

WABT

Validate a WebAssembly artifact and decode it into WAT, its text representation.

WAT exposes instructions and structure. It is not the original C, Rust or other source.

Built into REA

JavaScript analysis

Inspect modules, imports, source maps and Electron IPC relationships.

Static inspection can run without a native decompiler. Browser observations expose the client side.

06 / Network evidence

A capture tells a story
at the packet level.

TShark

Wireshark's command-line packet analyzer: select fields, apply filters and decode protocols.

Useful for inspecting addresses, DNS, TLS names and protocol-specific fields in a capture.

capinfos

Summarize capture-file metadata and statistics.

Helps describe the recording that the detailed packet inspection refers to.

REA's packet-inspection workflows read saved captures. Missing packets or encrypted payloads remain limits of the evidence.

Network / application-level traffic

Requests. Responses.
The conversation between them.

Fiddler Everywhere

Inspect web traffic and retain sessions for later analysis.

REA reads saved SAZ captures. Live Everywhere traffic uses its separate MCP integration.

mitmproxy

A programmable traffic-inspection proxy with saved flow recordings.

REA's native mitmproxy capture reader uses caller-supplied mitmdump on Linux.

Also useful: a browser-exported HAR file, containing a recorded request log.

Reading a retained capture does not repeat its requests or fetch the recorded URLs.

07 / The supporting layer

Install for the question
you actually need to answer.

Node.js / npm

The runtime and package tooling used to launch and distribute REA.

Our local launcher selects its own Node runtime, separately from the shell default.

Java JDK

A prerequisite for Java-based tools such as Ghidra and JADX.

Use the version required by the selected tool release.

Per workflow

Other prerequisites

Some paths need Python, OS utilities, debugger permissions or device access.

Host support belongs to each REA integration, even when the underlying tool runs on more systems.

Many metadata, archive and managed-code inspections are built into REA. “Supported by REA” and “configured on this machine” are separate facts.

DIVULGE / current integration boundaries

Three jobs.
Three explicit paths.

REA 6.8.0 adapter

Original-file evidence

REA measures byte entropy over a selected region of the original artifact.

DIVULGE retains the canonical evidence bundle, identity and limitations.

Vendor pi32v2 tools

Instruction decoding

The vendor disassembler decodes a bounded selection of FM-1 application bytes.

On Windows, this path uses Python and the selected WSL distribution.

Rust checks citations and bounds. Model interpretations remain labeled inferences.

A small experiment / synthetic teaching data

The bytes stay the same.
The interpretation changes.

Observation / file offsets 0 and 1
34hex / offset 0
12hex / offset 1

Two bytes. Their order is recorded.

4,660

0x12 × 256 + 0x34 = 4,660

The first byte is the least significant.

Neither interpretation tells us what this field means. That needs a format declaration, surrounding structure or a controlled experiment.

The discipline behind the workbench

Keep three kinds of statement
visibly distinct.

Observed

What we have

“The bytes at this range are 34 12.”

Retain the artifact identity, exact location and operation that read them.

Inferred

What we think

“This may be a length field.”

Connect the interpretation to its evidence and possible alternatives.

Unknown

What comes next

“Its intended meaning is unresolved.”

Keep the open question and the probe that could answer it.

A good investigation preserves uncertainty. It also gives the next person enough context to challenge the explanation.

09 / Our working loop

You steer the question.
We keep the answer inspectable.

Start with something answerable.

“What does this selected firmware region contain?” is a useful first question. It identifies a subject and the kind of evidence an answer will need.

Each cycle retains the question, selected bytes, tool output, interpretation and next probe. Saved replay lets us review the investigation at a human reading pace.
